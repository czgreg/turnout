## 1. 有没有"类似 QUIC"的问题

QUIC 的问题本质是"UDP 装进 TCP 隧道后被拥塞控制叠加拖垮"。按同样思路查了所有走代理的
UDP：

- 24h 内走代理且没被拒绝的 UDP：2337 条到 443（已由 `c7c4c05` 拒绝），**只有 2 条**到
  19302（Google STUN，WebRTC 打洞）。没有别的 UDP 业务在走代理。
- STUN / WebRTC 量极小，且 WebRTC 会自己回退到 TCP / TURN，不建议处理。
- 节点协议：hutao 35 个是 anytls，momo / wodi 是 trojan / ss。trojan 的 UDP 同样跑在 TCP
  上，`c7c4c05` 对所有走代理的 UDP 443 一律拒绝，不分协议，已覆盖。

结论：同类问题只有 QUIC 这一个，已修复。剩下的问题都不在"传输层被拖慢"，而在**连接被
打断**（重载、入口故障）和**故障切换速度**。

## 2. 问题详述与方案

### 2.1 P0 热重载风暴

**现象**（healthwatch 24h 汇总）：

```
reloads       69 hot reloads (0 failed)
change cause  routing 3 | probing 3 | named applied 69 | named deferred 104
```

- 每次重载约 0.6–1.2 秒，mihomo 用 `PUT /configs?force=true` 重建全部分组，**已建立的代理
  连接全部重置**（`internal/dataplane/control.go` 注释中有压测实测）。
- 触发来源几乎全是"named applied"：wodi 仅剩的 3 个香港节点（TBT / TC / TAT）作为 hutao 的
  跨订阅备用节点来回进出，单个探测终端一天里备用节点换了 22 次；ai-pool 成员也在美国节点
  之间小幅变动。
- 现有去抖（`scorer.go` 中 named-pool coalescing）最多推迟 2 轮，之后照样应用，所以持续
  抖动 = 每 10–15 分钟一次重载。
- 之前和你核对过：重载对"打开网页"影响概率低（约 1%），**真正受害的是长连接**——看视频、
  大文件下载、ChatGPT 的 WebSocket（`ws.chatgpt.com`）几乎每次都会被打断一次。

**Clash 类做法**：Clash / mihomo 的主流配置极少在运行中改分组成员，节点增减交给
`proxy-providers` 的 `health-check` + `filter` 在**不重载**的情况下处理；切换完全靠组内的
alive 位。

**方案**：

1. **仅备用节点变化不触发重载。** `computeBackups` 的结果变化若是本轮唯一变化，只记录为
   "待应用"，跟随下一次因主线路 / 探测集合变化的重载一起下发。
2. **例外（立即重载）**：某个订阅的**全部**备用节点都已 `alive=false`（此时备用确实失效，
   入口故障时主备会一起挂）。
3. ai-pool 成员变化同理：移除的成员仍存活 → 不单独重载；移除的成员已死 → 维持现有
   `namedChangeUrgent` 的立即应用。

**预期**：重载从约 69 次/天降到约 6–10 次/天（routing 3 + probing 3 + 少量紧急）。

**风险**：备用节点最多滞后到下一次重载；而备用只在主节点失效时才用到，且 mihomo 的 fallback
组会跳过已死的备用。最坏情况是主备同时失效，第 2 条例外规则兜住。

**验证**：healthwatch `change cause` 中 `named applied` 应降到个位数；单元测试覆盖"仅备用
变化 → 不重载 / 备用全死 → 立即重载"。

### 2.2 P0 ai-pool 被清空成 DIRECT

**现象**：

```
08:06:18  nodescorer: pool updated + hot-reloaded          ← hutao 美国节点全死，ai-pool 成员被算成空
08:11:17  named-pool change awaiting confirmation round=1 applied_members=map[ai-pool:[]] proposed=[5 个美国节点]
08:16:18  nodescorer: pool updated + hot-reloaded          ← 10 分钟后才恢复
```

- 成员为空时，renderer 输出 `select [DIRECT]` 占位（`groups.go`），AI 域名在国内直连，必然
  失败。
- 恢复路径（空 → 有成员）被当成普通变更去抖，又多等了一轮（5–10 分钟）。
- 同一窗口 AI 线路有 72 次拨号超时（`fb-ai-*`，到 hutao 的美国入口）。

**Clash 类做法**：分组为空时用 `empty-fallback`（默认 `COMPATIBLE`），而不是悄悄换成
DIRECT；成员不因短时故障被移出，靠 alive 位跳过。

**方案**：

1. **分类池不清空**：本轮没有任何合格成员时，保留上一轮已应用的成员（它们多半几分钟后就
   恢复，mihomo 的 alive 位会自动重新启用），不输出 DIRECT 占位。DIRECT 占位只留给"从来
   没有过成员"的冷启动。
2. **空 → 非空视为紧急**：`namedChangeUrgent` 增加一条——旧成员为空、新成员非空时立即
   应用。

**验证**：单元测试覆盖"全部成员死亡 → 保留原成员"和"空 → 非空 → 不去抖"；线上观察下次入口
故障时日志里不再出现 `rendering DIRECT stub`。

### 2.3 P1 故障切换更快：健康检查超时与失败计数

**现状**：分组只配了 `url` / `interval: 10` / `lazy`，没有 `timeout`、`max-failed-times`，
都用默认值（按 mihomo 文档，`max-failed-times` 默认 5；`timeout` 示例值 5000 ms）。

- 入口故障时一次探测要等满超时才判定死亡，再加上间隔 10 秒，前 10–20 秒的新连接仍拨向死
  节点。
- `max-failed-times` 是 mihomo 的被动检测：组内**真实连接**连续失败 N 次即强制做一次健康
  检查，不必等下个周期。默认 5 次偏保守。

**方案**（只作用于终端主备组 `fb-*` 和 `dns-out`）：

```yaml
timeout: 2000          # 毫秒；hutao 节点 p95 约 150 ms，美国约 230 ms，有 8 倍余量
max-failed-times: 2
expected-status: 204   # 与 generate_204 对应，避免被劫持页面的 200 当成存活
```

`default-pool`（全部候选，非 lazy，60+ 成员）不改，免得对机场探测流量放大。

**预期**：入口故障下的不可用窗口从 10–20 秒降到约 2–5 秒；11:00 那类"前 1 分钟连接
失败"的情况会明显缩短。

**风险**：`timeout` 过短可能把偶发慢的节点误判为死；2000 ms 远高于实测 p95，误判概率低。
可在配置里暴露 `url_test.timeout` 以便回调。

**验证**：渲染测试 + 节点 `mihomo -t`；线上观察下次入口故障时终端的切换时延（mihomo 日志里
从首个错误到首个经备用节点成功连接的间隔）。

### 2.4 P1 AI 线路缺乏跨订阅备用（运维）

- 24h 内 185 次 AI 拨号超时：08:00 段 72 次、11:00 段 37 次、22:50 段 71 次，全部是 hutao
  美国入口（端口 14003 的三个地址）。
- ai-pool 只收美国节点，而目前只有 hutao 有存活的美国节点，所以跨订阅备用对 AI 线路无效，
  `/api/pool/terminal` 中 ai-pool 的主备也都是 hutao。
- **改代码解决不了**，需要运维补一家能用的美国节点（或让 wodi / momo 的美国节点恢复）。
  按 CLAUDE.md，订阅列表由运维维护，网关这边不动。

一个可选但**不推荐**的代码方案：AI 线路的备用节点放宽到日本节点。这会让同一终端访问 AI 时
出口 IP 在美国和日本之间切换，违背"一个终端一个 AI 出口 IP"的反风控设计，且部分 AI 服务
对地区敏感。

### 2.5 P2 客户端写死的 DoH 被墙

- 24h 内 DIRECT 拨号失败 51 次，其中 23 次是 `1.1.1.1:443`（同一台终端，每小时 :50 左右
  一次，像是某个应用或浏览器的 Secure DNS 定时探测），另 23 次是 `init.push.apple.com:443`。
- 白名单模式下 `1.1.1.1` 不在白名单 → `MATCH,DIRECT` → 被墙 → 客户端等超时后才回退系统
  DNS。
- 节点自己的 dns-out 上游也是 1.1.1.1 / 8.8.8.8，但它们走代理，不受影响。

**Clash 类做法**：常见规则集把公共 DoH（`1.1.1.1`、`1.0.0.1`、`8.8.8.8`、`8.8.4.4`、
`dns.google`、`cloudflare-dns.com`）放进代理规则。

**方案**：通过现有 `PUT /api/whitelist` 追加 `ip_cidr`（`1.1.1.1/32`、`1.0.0.1/32`、
`8.8.8.8/32`、`8.8.4.4/32`）和 `domain_suffix`（`dns.google`、`cloudflare-dns.com`）。
不改代码，会触发一次重载。

`init.push.apple.com` 属于 Apple 推送，量小，先不处理，持续观察。

### 2.6 P2 打开 `tcp-concurrent`

按 mihomo 文档："启用 TCP 并发连接，将会使用 dns 解析出的所有 IP 地址进行连接，使用第一个
成功的连接"。这是 Clash 配置模板里的常见默认项，主要改善 DIRECT 访问多 A 记录站点，以及
用域名表示的机场入口（hutao 一个域名背后有多个 AWS 东京地址轮换）。renderer 顶层加一行
即可，风险低。

### 2.7 P3 实验：anytls 预热会话

- anytls 在一条 TLS 会话上复用多个流，默认 `idle-session-timeout: 30`、`min-idle-session: 0`：
  空闲 30 秒后会话全部关闭，下一个新连接要重新做一次到入口的 TCP + TLS 握手。
- 这部分时延叠加在"打开网页"的首个请求上。办公场景下终端经常空闲几十秒，可能每次都踩到。
- 方案：给 anytls 节点注入 `min-idle-session: 2`（每个节点常驻 2 个空闲会话）。
- **先做 A/B 实验再决定**：在节点上用临时 mihomo（和之前的带宽测试同样方法），空闲 60 秒
  后测首个请求的 TLS / TTFB，对比默认值和 `min-idle-session: 2`。收益不到 100 ms 就不做，
  免得增加机场入口的长连接数。

## 5. 机场侧限制体检

机场为了保证整体性能和稳定性，常见的限制有：UDP / QUIC 限速、单连接限速、端口封禁、
审计规则（屏蔽测速站、BT、挖矿等）、并发连接数 / 设备数限制、空闲连接回收、计费倍率、
流量和到期时间。QUIC 已在 `c7c4c05` 处理，其余逐项实测。

**方法**：在 10.100.6.15 上起一个临时 mihomo（只读生产配置，DNS 与生产一致，不碰生产实例），
每个被测节点一个钉死的 loopback 监听，依次测：单流与 4 流下载（dl.google.com）、测速站 /
BT tracker / GitHub Releases、portquiz.net 的 8 个端口、80 个并发 TLS 握手、空闲 60 / 180 /
330 秒后复用连接。被测节点：hutao 日本、hutao 美国、momo 香港、wodi 日本、wodi 台湾 6x。

| 限制 | hutao 日本_BGP_A | hutao 美国_BGP_A | momo 香港06_WD | wodi 日本TAT.2x | wodi 台湾TC.6x \| 专线 |
|---|---|---|---|---|---|
| 单流下载 | 119 Mbps | 120 Mbps | 168 Mbps | 99 Mbps | **0.0 Mbps** |
| 4 流下载 | 563 Mbps | 403 Mbps | 351 Mbps | 220 Mbps | **0.2 Mbps** |
| 测速站 / tracker / GitHub | 全部可达 | 全部可达 | 全部可达 | 全部可达 | speedtest.net 403，其余超时或很慢 |
| 封禁端口 | 22、25、465、587、993 | 22、25、465、587、993 | 无 | 22、25 | 25 |
| 80 并发握手 | 80/80 | 80/80 | 80/80 | 80/80 | **53/80，25 个被重置** |
| 空闲后复用 | 180 s 存活，330 s 断开 | 同左 | 同左 | 同左 | 同左 |
| 计费倍率（节点名） | — | — | — | 2x | **6x** |

### 5.2 解读

1. **坏节点在路由池（新 P0）**。`wodi/台湾TC.6x | 专线` 几乎不通，但它对 generate_204 的
   小探测能通过（p95 约 520 ms，低于 800 ms 门槛），所以评分把它当合格节点放进了路由池。
   当前渲染配置里，1024 个终端分组中有 123 个以它为主节点，另有 7 个主备组以它为备用，
   dns-out 也会用到它。这些终端访问白名单网站会极慢或失败，而且 6 倍计费在消耗 wodi 的流量。
   这正是"评分只看延迟不看带宽"的后果，之前提的带宽评分从"锦上添花"变成了必需。

   **方案**：
   - `data_plane.url_test` 增加 `node_exclude_pattern`（对应 Clash 的 `exclude-filter`；Go 正则
     不支持前瞻，无法写进 `node_pattern` 里）。默认建议排除 `[3-9]x|\d{2,}x|倍`
     这类高倍率节点。
   - 入池前加最低带宽门槛：scorer 对每个候选节点低频（例如每 6 小时、每节点 3 秒）做一次
     单流下载，低于门槛（例如 10 Mbps）的不进路由池和备用名单。复用 probe-out 监听即可，
     不必另起实例。这也回答了最早"优先选带宽高的节点"的需求：门槛先挡住坏节点，排序仍按
     延迟。
2. **单连接限速**：hutao 日本和美国的单流都是约 120 Mbps，而两者 RTT 相差一倍（约 100 ms 和
   220 ms）。如果只是延迟造成的窗口限制，速度应该差一倍，所以更像是机场按连接限速在
   120 Mbps。高于终端的 100 Mbps 网卡和 1080p / 4K 需求，**不影响使用，不处理**。
3. **端口封禁**：hutao 封了 SSH 和邮件端口，这是机场防滥发垃圾邮件、防扫描的常见做法。
   48 小时生产日志中没有走代理的此类连接，目前无影响。潜在影响是 `git@github.com`
   （SSH 22，`geosite-github` 在白名单）和走代理的邮件客户端。
   **方案**（二选一）：渲染时对 `DST-PORT` 为 22 / 25 / 465 / 587 / 993 的走代理流量改用
   允许这些端口的订阅（当前是 momo）；或者只在文档里告知开发用 `ssh.github.com:443`。
   使用量为零，建议先做文档，等有需求再改规则。
4. **审计规则**：测速站、BT tracker、GitHub Releases 在 4 个正常节点上都可达，**未发现
   审计屏蔽**。
5. **并发连接数**：4 个正常节点 80 个并发握手全部成功。当前生产只有 4 个终端在用代理、
   单节点最多 9 条连接，离限制很远。**暂不处理**；等终端数接近 `capacity.sustained_max_users`
   （50）时，用 `scripts/stress.sh` 再测一次。
6. **空闲回收**：3 家订阅、5 个节点全部是 180 秒存活、330 秒断开，完全一致。3 家机场不太可能
   设成同一个值，更可能是目标服务器（Google 前端）关闭了空闲的 HTTP/1.1 连接。**不是机场
   限制，不处理**。应用会自动重连。
7. **流量与到期**：hutao 已用 76.6 / 537 GB，**2026-11-10 到期（还有 12 天）**，目前承担几乎
   全部代理流量；wodi 19.3 / 537 GB，11-24 到期；momo 的订阅信息里流量和总量都是 0，无法
   判断余量，11-15 到期。需要运维提前续费或调整主力订阅。

### 5.3 对优先级的影响

- 5.1 第 1 条升为最高优先级，排在重载风暴之前：它是持续性的，12% 的终端每次访问都慢，
  不是偶发的连接中断。
- 其他限制要么不影响使用（单连接限速、并发、空闲回收），要么目前没有流量（端口封禁），
  都不需要马上改代码。
